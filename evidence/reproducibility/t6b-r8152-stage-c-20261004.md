Target: SBA6D / vendor Linux 5.4.238 ARM64.

Driver source: Realtek-compatible r8152 v2.21.4,

USB NIC: Realtek RTL8156, `0bda:8156`.

## Background failure

An earlier r8152 build passed ordinary metadata checks and loaded, but Oopsed while
binding the RTL8156.

The useful pstore fault was:

`__rtl8152_set_mac_address+0x9c`

The old final ELF accessed:

```text
ldr x0, [x21,#0x2e8]
```

which treated `netdev->dev_addr` as offset `0x2e8`.

Vendor-kernel evidence established `dev_addr=0x318`. The fault was therefore classified
as a `struct net_device` layout mismatch rather than a symbol-version mismatch.

Important metadata evidence from the investigation:

- vendor `module_layout` CRC: `0x3a3eb6e9`
- old r8152 `module_layout` CRC: `0x3a3eb6e9`
- vendor `alloc_etherdev_mqs` CRC: `0x224a0869`
- candidate `alloc_etherdev_mqs` CRC: `0x224a0869`
- vendor `register_netdev` CRC: `0xe17e26a0`
- candidate `register_netdev` CRC: `0xe17e26a0`

This is retained as a concrete example that CRC equality alone did not protect against
wrong inline structure offsets.

## Canonical build strategy

The successful build reused the T6B AX88179 compatibility environment instead of
reconstructing the vendor ABI from pristine 5.4.238.

Key reusable conditions:

- WEXT-aware `net_device` compatibility model
- 32-byte opaque region immediately before `dev_addr`
- `dev_addr=0x318`
- `netdev_priv=0x8c0`
- `netdev_ops=0x1f8`
- `ethtool_ops=0x200`
- embedded `struct device` at `0x510`
- TX queue base `0x3c0`, stride `0x140`, queue state `+0x90`
- target Image-derived symbol CRC reference
- global KCFLAGS preserving TRACEPOINTS/TRACING/EVENT_TRACING/MODULES_TREE_LOOKUP,
  including generated `.mod.c`
- vendor-compatible module management layout: size `0x340`, init `0x150`,
  cleanup `0x328`

An iperf2 client attempt failed because the peer was running iperf3; this is a protocol
mismatch and not driver evidence.

## Supported claim

This evidence supports:

**RTL8156 / r8152 on SBA6D: module load, USB bind, MAC setup, netdev creation,
interface open, 2.5GbE physical link, bidirectional basic IPv4 datapath and short iperf3
throughput validation all passed without r8152-related WARN/Oops/panic.**

The best observed short-run transmit throughput is 2.27 Gbit/s at P1 with zero
retransmissions.

Still not established:

- long-duration stability,
- reverse-direction iperf3 throughput,
- repeated hotplug/reload endurance,
- performance across other firmware/hosts/cables.
